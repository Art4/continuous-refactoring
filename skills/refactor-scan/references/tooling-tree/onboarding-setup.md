# `onboarding-setup`

Node on the generic **tooling tree** (`../tooling-tree.md`); parents, edges, and the diagram live there. Vocabulary: `CONTEXT.md` (**node**, **required edge**, **recommended edge**).

- **Name:** Onboarding Setup
- **Tool:** none — this is the suite's own state, not a third-party tool.
- **Purpose:** the continuous-refactoring loop's own state and configuration exist for this person and target, so a pass has somewhere to read/write its bookkeeping and knows its ticket-create-mode and MR-create-mode.
- **Fulfilment check:** the Bookkeeping pointer resolves to an existing `bookkeeping.md` (see `../../../continuous-refactoring/references/refactoring-bookkeeping.md` for how the pointer is resolved — the config file's `Bookkeeping:` field, else a line in the instruction file; the Refactoring Notes are `.scratch/refactor/` by default).
- **MR scope:** none — never proposed. `continuous-refactoring`'s own onboarding step (step 0 of the dispatcher) fulfils this node before any Track runs, by running the interview in `../../../continuous-refactoring/references/onboarding-setup-interview.md` and writing `.scratch/refactor/config.md` (the Bookkeeping pointer, with `Ticket-create-mode` and `MR-create-mode` set from that interview) and `bookkeeping.md` (see `../../../continuous-refactoring/references/refactoring-bookkeeping.md` for the files' shapes; there is deliberately no stored cadence for this loop itself, it never triggers itself) plus, where missing, `docs/agents/issue-tracker.md` and `docs/agents/triage-labels.md`. The node stays in the tree as the root prerequisite every other node hangs beneath; a scan only ever sees it already fulfilled, because `refactor-loop` and `continuous-housekeeping` abort when the pointer doesn't resolve to a `bookkeeping.md`.
