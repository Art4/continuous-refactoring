# Reference: manual tree-walk prompt (python3 unavailable)

When `python3` can't run — not installed, or executing it isn't permitted in the current harness — `refactor-scan` step 4 and `continuous-refactoring`'s outlook step dispatch a sub-agent with the prompt below instead of running `tooling_tree.py`. Fill in `{TARGET_REPO}` (the target repo's path), `{REFACTORING_NOTES}` (the Refactoring Notes' path relative to `{TARGET_REPO}` — read `{TARGET_REPO}/AGENTS.md`, then `{TARGET_REPO}/CLAUDE.md`, for a `` Refactoring Notes: `<path>` `` line; `docs/refactoring` if neither names one — see `skills/continuous-refactoring/references/refactoring-bookkeeping.md`), and `{N}` (`all` for the proposal step — the set is never capped — `1` for the outlook) before dispatching. With no sub-agent mechanism available, run the same steps yourself inline instead.

---

Read `skills/refactor-scan/references/tooling-tree.md` in full, plus the active language specialization's tree doc if one applies to `{TARGET_REPO}` (PHP: `skills/refactor-scan/references/php-tooling-tree.md`). Build the combined edge table from both, keeping the order rows appear in the docs (generic root first, then the specialization).

For each node, in that order:

1. Evaluate its Fulfilment check — written under the node's own heading, or in the file its stub points to if the node has already been extracted (see `php-tooling-tree.md`'s *Nodes* preamble — the stub left behind names the extracted file) — against `{TARGET_REPO}` directly. Read the files it names; don't guess. Judge against the node's Purpose statement rather than trusting a parser's raw dependency-name match alone — a tool under a different name that genuinely serves the Purpose counts as fulfilled.
2. A node is unblocked once every one of its **required** edges points to an already-fulfilled parent. Any node with one or more **resolved** edges into it (today: `structural-scan`, and PHP's own `php-safety-net` feeding it) is different: each resolved edge clears once its parent is fulfilled *or* a file exists at `{TARGET_REPO}/{REFACTORING_NOTES}/out-of-scope/<node>.md` — once every resolved-edge parent clears one way or the other, the node is **resolved**. The same rule applies one hop down: `php-safety-net` is itself resolved the same way, from its own nine resolved-parents, and that resolved-ness is exactly what `structural-scan` reads as one of *its* two resolved-parents. Check this before the ordinary already-fulfilled skip below: a resolved-gated node stays proposable every pass once open, it's not a one-time node — except an aggregation node like `php-safety-net`, which the aggregation-node paragraph below excludes from ever being proposed regardless of its resolved state. A **required** edge whose *parent* happens to be one of these resolved-gated nodes (today: `secret-detection`, required on `structural-scan` itself) reads that parent's "fulfilled" state exactly as computed above — the gate having opened, not a one-time delivered node — same as any other required parent; no separate rule needed.
3. Skip a node that's already fulfilled — except a node gated purely by resolved edges (`structural-scan`), which the point above already covers.
4. Skip a node (other than a resolved-gated node like `structural-scan`) that has a file at `{TARGET_REPO}/{REFACTORING_NOTES}/out-of-scope/<node>.md` — it was explicitly rejected and stays out until that entry is reversed (removed); don't re-propose it on the strength of newly-fulfilled required parents alone.
5. A node with one or more **recommended** edges is unblocked (by this point 5, on top of point 2) only once every one of those parents is *decided* — meaning fulfilled, or rejected. "Rejected" here includes a parent that's rejected outright (a file at `{TARGET_REPO}/{REFACTORING_NOTES}/out-of-scope/<parent>.md`) **and** a parent permanently closed because one of *its own* required parents is (recursively) decided-rejected the same way — walk that parent's required chain the same way you'd check point 2, just looking for a rejection instead of a fulfilment. A recommended parent that simply hasn't been reached yet (still blocked by its own required edges, neither fulfilled nor rejected) counts as undecided too — the same as one that's sitting unblocked-but-unactioned. Note any node you withhold this way, and which parent(s) it's still waiting on — the caller needs that to explain a gap in the results, not just a silently shorter list.

A node whose only outgoing edge is itself a `resolved` edge into another node (an **aggregation node** — today: `php-safety-net`) is never collected into the proposable/withheld sets below, even once resolved — it exists only to be checked when walking its child's own resolved edges (point 2), never as a candidate or a withheld entry in its own right.

Two ordinary (non-aggregation) nodes are never a candidate either, regardless of their own fulfilled state: `static-code-analyzer` (pure plumbing, no real-world action of its own) and `psalm` (recognition-only — fulfilled when a project has already adopted it instead of PHPStan, but never suggested as a new adoption, the same fait-accompli shape Pest already gets for `phpunit`).

Collect nodes in table order until you have `{N}` that are unblocked (per points 2 and 5), not yet fulfilled, not rejected, and not an aggregation node or `static-code-analyzer`/`psalm` (per the two paragraphs above), or the table runs out — `{N}` = `all` means don't stop early. `git` is never a candidate either. This set is the fallback for `tooling_tree.py`'s `next` field; the withheld set from point 5 is the fallback for its `withheld` field.

**Filling `Open` (Safety Net / Guardrails Track):** When this prompt is used to fill a Track's `Open` list, the agent evaluates every node of the Track's scope by judgement (all Fulfilment checks, including gate nodes), then records every unresolved node of the scope into `Open` in table order, blocked nodes included. A completed scan still records `Last scan`, even when everything is already resolved — `Open` is empty in that case. When a rejection is recorded, every node closed by that rejection (per the script's `closed_by_rejection()` — nodes whose required or required-any ancestor is effectively rejected) also leaves `Open`, with no new files. Reversing a rejection makes the next scan bring those nodes back.

Return only this: for each node in the set, its **Name** (the `**Name:**` field under its heading — never the node's slug) and one line — either why it's unblocked, or its Purpose, whichever the caller asked for; then, for the proposal step only, each withheld node's Name and which parent Name(s) it's waiting on. Nothing else: no restated edge table, no exploration narrative.
