# PHP Minimum Version

The Tool for the Role Runtime Floor in the PHP Pack. It has no third-party tool: the gap detection is its own.

**Why this order.** It needs `rector-php-set` fulfilled, a level truly landed and not merely decided: a rejected `rector-php-set` leaves it unproposable for good. It is a Guardrails Stage, workable only once the Safety Net is fulfilled.

### `php-minimal-version`

- **Purpose:** a **Floor correction** only, never a **Floor raise** (`CONTEXT.md`). `composer.json`'s declared PHP floor (`require.php`) understates what the codebase already contains once `rector-php-set` has landed a PHP-version rule set: the rewritten syntax needs that version to run, so declaring the floor is telling the truth, not a behavior change. It never proposes committing the application to a newer PHP than its own code needs; that would be a **Breaking change**, out of scope for anything shipped under the refactor label. A `require-dev` tool's own PHP requirement (PHPStan, Rector, …) never drives this floor either: Composer only needs the platform running `composer install` to satisfy a dev tool, never the package's declared floor. So neither "a tool needs a newer PHP" nor "CI runs the quality tooling under a newer PHP image" is ever a signal here. Nothing but the application's own code needing it, as `rector-php-set`'s landed syntax shows, raises `require.php`.
- **Fulfilment check:** `composer.json`'s declared PHP floor (`config.platform.php` if pinned, else the lower bound of `require.php`) is at least the PHP-version level `rector-php-set` (`rector.md`) has applied. The applied level is read from Rector's config at the repo root (`rector.php` or `rector.neon`); the constant is `LevelSetList::UP_TO_PHP_XY` (`UP_TO_PHP_82` means PHP 8.2). If no level has been applied yet, or the floor is unknown (no `composer.json`, or neither `require.php` nor `config.platform.php` parses), the Stage counts as fulfilled: there is nothing to correct, and an unknown floor blocks nothing.
- **MR scope:** narrow: a `composer.json` `require.php` edit, plus the CI job that tests the app itself if a single unified job exists. No verification beyond the ordinary CI gate; `rector-php-set`'s own Fulfilment check already means "fully applied, no remaining findings". Also add the Housekeeping line below to the target's Housekeeping template (`../../implement-point.md`, *Slices every kind of ticket can have*). A Stage already fulfilled the very first time it is evaluated never gets a merge request of its own; its line then reaches the template through the Housekeeping Track (`../../../../continuous-housekeeping/references/housekeeping-track.md`, step 4).
- **Housekeeping:** check whether a newer PHP patch or minor release exists for the PHP version `composer.json` declares as its minimum, and update the declared version if so.
- **Re-triggering:** the Fulfilment check compares against a moving target. `rector-php-set` re-levelling upward later (its MR scope: "adopted in levels, one MR per target PHP version bump") can leave a previously sufficient floor behind. A scan the call asks for, or Housekeeping's re-check of the tooling Tracks, finds that and offers a ticket again.
- **Reversal:** a recorded rejection of this Stage that carries a PHP version as its blocker (`Blocker: PHP >= X.Y`, `../../rejection.md`) is offered for reversal once the target's floor reaches that version, like any other rejection.
