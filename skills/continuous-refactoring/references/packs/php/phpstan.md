# PHPStan

The recommended Tool for the Role Static Analysis in the PHP Pack. It has a minimum runtime of PHP 7.0 (`pack.json`). One file for the whole family: the level chain, the deprecation rules and the Psalm equivalence are one story. The Stages are `phpstan-level-0`, `phpstan-level-1` through `phpstan-level-10` and `phpstan-deprecation-rules`.

**Why this order.** The levels are a chain, one step at a time, with the same rules throughout; no level is skipped. Levels 0 to 5 are Safety Net Stages, level 6 on and the deprecation rules are Guardrails Stages, workable once the Safety Net is fulfilled. Level 5 is the chain's fork point: Deprecation Rules start from it. Levels above 5 stay fully proposable; the chain just stops being load-bearing for the Safety Net. Levels 6 and up start the stricter array-typing rules, a bar not worth clearing before ordinary structural refactoring can begin. Psalm Taint Analysis and Rector Type Coverage use levels 4 and 3 as their thresholds. Two levels wait for a Rector Stage to be decided, because the rewrites shrink their baseline before it is fixed by hand: level 4 for Rector Dead Code, whose rules remove what level 4 reports (unreachable code, conditions and type checks that are always true or false), and level 5 for Rector Type Coverage, so the argument types level 5 checks are measured once against the declared types rather than fixed against docblocks the rewrites later replace. A rejected Rector Stage releases the level; it just goes in without the rewrites.

### `phpstan-level-0`

- **Purpose:** static analysis introduced green at level 0. A target on Psalm has the Role Static Analysis filled by Psalm (the Stage `psalm`), and PHPStan is then not proposed (*PHPStan and Psalm* below).
- **Fulfilment check:** one of:
  - **PHPStan path (canonical):** `phpstan/phpstan` is present as a dev dependency, **or** installed ephemerally at CI runtime only (a CI job body containing both a `composer require[--dev] phpstan/phpstan` invocation and the `vendor/bin/phpstan analyse` invocation counts like a committed dependency; some targets deliberately keep the app's own manifest free of pure-analysis tooling). `phpstan.neon` / `phpstan.neon.dist` at the repo root declares a level: `level: 0` at introduce time, but **a project already advanced to level 1 or higher satisfies this too**, since every level-0 check is a strict subset of any higher level's, and the Stage is re-checked from the current config on every scan rather than pinned to the level it was first delivered at. A committed baseline file exists at the fixed path `phpstan-baseline.neon` (repo root). `vendor/bin/phpstan analyse` (with the baseline included) exits 0 without errors. **And**, once `ci-runner` is fulfilled, a CI job invokes `vendor/bin/phpstan analyse` (a self-wired CI gate; with no CI yet, local adoption alone still fulfils the Stage). The CI check is level-independent, so it lives here and is not repeated on levels 1 to 10. `phpstan.neon` takes precedence when both files exist, matching PHPStan's own auto-discovery order (the same "committed default, locally overridable" convention read for `phpunit.xml.dist`, `psalm.xml.dist` and `phpmd.xml.dist`). OR
- **Config (PHPStan path):**
  - `phpstan.neon`, committed at the repo root by this Stage's own merge request (not `phpstan.neon.dist`: a fresh adoption always writes the non-`.dist` name; the check reads either, for a target that adopted PHPStan with `.dist` before). Minimal exact content:
    ```neon
    parameters:
        level: 0
        paths:
            - src
        excludePaths:
            - vendor
    includes:
        - phpstan-baseline.neon
    ```
    `paths` is resolved from `composer.json` `autoload` / `autoload-dev` (`psr-4` and `psr-0` directories; `files` is ignored). If no autoload directories are declared, the fallback is `src`. Additional source roots (such as `tests/` when not already covered) may be appended when present. `excludePaths` always contains `vendor`. `includes` references the baseline at the fixed path `phpstan-baseline.neon`; the line is present in `phpstan.neon` from this merge request onward.
  - `phpstan-baseline.neon`, committed at the repo root. Auto-generated, never hand-edited. Generated by `vendor/bin/phpstan analyse --generate-baseline=phpstan-baseline.neon` (overwrites if present). It contains `parameters.ignoreErrors` entries for all violations at the current level; when no violations remain the file is still committed but holds an empty ignore list (*Empty baseline*).
  - Dependency versioning follows the target's pinning policy; if none is declared, use a `^` caret range with a committed `composer.lock`.
- **MR scope:** the dependency (`composer require --dev phpstan/phpstan`), `phpstan.neon` with `level: 0` and the initial baseline generation (`--generate-baseline`), committed together and leaving `vendor/bin/phpstan analyse` green (exit 0). Shrinking the baseline belongs to the level Stages, not this merge request. No level above 0 and no additional rulesets are introduced here. If `ci-runner` is already fulfilled when this merge request lands, it also wires `vendor/bin/phpstan analyse` into CI as a gate, as PHPUnit's does. No rejection is written for Psalm: the PHPStan path's own check (no `vimeo/psalm` dependency) is the inspectable record of the choice.
- **Verification:** `composer install` succeeds locally; `vendor/bin/phpstan analyse --error-format=table` (or plain `vendor/bin/phpstan analyse`) exits 0 with the committed baseline included.

### `phpstan-level-1` through `phpstan-level-10`

- **Names:** `phpstan-level-N` is "PHPStan Level N" for each `N` from 1 to 10.
- **Purpose:** raise the analysis level one step at a time, straight through the chain, same rules throughout, no redesign at any level.
- **Fulfilment check:** the immediate predecessor level is fulfilled **and** its baseline is **empty** (*Empty baseline* below). Then: bump `level` in `phpstan.neon` by exactly one (`0 → 1`, `1 → 2`, …, `9 → 10`), regenerate `phpstan-baseline.neon` via `vendor/bin/phpstan analyse --generate-baseline=phpstan-baseline.neon`, and `vendor/bin/phpstan analyse` is green. Levels are never skipped; one merge request raises exactly one level. **The Ratchet:** a level is fulfilled only while its baseline is empty. A level the target has set up whose baseline still holds entries is not fulfilled; its ticket is "PHPStan Level N: shrink the baseline" (`../../track-scan.md`, step 4), and the next level requires it. On a target on Psalm none of the levels applies: PHPStan is not proposed (*PHPStan and Psalm*).
- **Empty baseline, operationally:** `phpstan-baseline.neon` is **absent** at the repo root **or** the file exists but `parameters.ignoreErrors` is absent or an empty array (no `message:` entries). Both count as empty. A file that exists and holds one or more ignore entries is non-empty and blocks the next level raise. The scan parses the Neon file (or equivalently counts `message:` entries); an absent file is treated as zero entries. After the introducing merge request the file is normally present; absence is tolerated as empty for gating the next level, but after any successful analysis the committed state should include the file (an empty list when green without a baseline).
- **MR scope:** the level bump (a single integer increment), the regenerated baseline (overwritten in place) and only those source fixes that strictly reduce the new baseline's `ignoreErrors` count. Shrinking findings into the regenerated baseline is part of the same merge request: it commits the reduced baseline alongside the fixes that produced the reduction. Unrelated refactoring or feature changes stay out. The chain stays open above level 10: further levels are appended as new Stages with the same rules, not a redesign.
- **Stop conditions, when not to raise:**
  - The baseline is non-empty: the level it belongs to is not fulfilled and the next level waits; the level's own ticket is "PHPStan Level N: shrink the baseline", planned part by part (`../../design-point.md`, *Planning a baseline ticket*) until the baseline is empty and the next level is workable again.
  - The immediate predecessor level is not fulfilled: the scan does not propose out-of-order levels.
  - The target uses Psalm: PHPStan is not proposed (*PHPStan and Psalm*). Psalm strictness is governed by `psalm.xml`'s `errorLevel`, not by this chain.
  - CI is irrelevant to the gating: the Fulfilment check is local (`vendor/bin/phpstan analyse` green).
- **Verification:** after the merge request, `vendor/bin/phpstan analyse` exits 0 at the new level with the committed baseline; the `phpstan.neon` diff is exactly one `level:` line; `phpstan-baseline.neon` is regenerated and reflects the current violations at that level.

### `phpstan-deprecation-rules`

- **Purpose:** flag calls to deprecated APIs and functions, orthogonal to the level chain's strictness ladder; adopted once the codebase is far enough along the chain that deprecation noise is not drowned out by lower-level findings. A deprecated-API call is a finding this ruleset itself produces, not something a structural refactor could introduce or collide with. The tool is PHPStan's deprecation rule set: bundled rules PHPStan reports independently of `level`. It is proposed once the chain has reached level 5, a threshold set directly with the user and not tied to level 10's top.
- **Fulfilment check:** PHPStan's deprecation rules are enabled (the bundled deprecation ruleset or an equivalent extension) and the current `phpstan.neon` runs green with them on.
- **MR scope:** the dependency or config enabling the ruleset; no production-code change beyond fixing surfaced deprecations. Also add the Housekeeping line below to the target's Housekeeping template (`../../implement-point.md`, *Slices every kind of ticket can have*).
- **Housekeeping:** after any dependency update, re-run PHPStan and check for newly surfaced deprecation warnings (a dependency bump can start calling an API this ruleset did not flag before); fix in scope.

## PHPStan and Psalm

Psalm is a Tool of its own, recognized and never proposed, with one Stage, `psalm` (`psalm.md`); PHPStan is the recommended Tool for the Role Static Analysis.

- **A target on Psalm.** Once the Stage `psalm` is fulfilled the Role is filled by Psalm, PHPStan is out, and none of its Stages is proposed: the level chain is PHPStan-specific. A project that chose Psalm raises strictness via Psalm's `errorLevel` (8 loosest, 1 strictest). The agent hands in `psalm` as fulfilled, and `phpstan-level-0` only where PHPStan itself is there. If a repo later replaces Psalm with PHPStan, `phpstan-level-0` is fulfilled and PHPStan is the Tool in use again.
- **Co-presence.** If both analysers are present, PHPStan is the Tool in use and its Stages apply with the standard baseline and level rules; Psalm's Stage is harmlessly fulfilled too.
- **No other analyser fills the Role.** Only `vimeo/psalm` is recognized beside PHPStan. Other tools (Phan, Psalm plugins) are not treated as filling it.
- **What waits for the Role.** `rector-php-set` requires the Role Static Analysis, filled by either Tool, and `psalm-taint-analysis` requires PHPStan Level 4 or Psalm.
