# Generic tool-tree root; structural scanning as a gated tree node

> Amends [ADR-0005](0005-tooling-tree-not-baseline-skill.md): `git`'s tree entry moves to a new generic root (`docs/tooling-tree.md`); PHP's `composer`/`ci-runner` re-parent from `git` to a new `loop-config` node.
>
> Amended by [ADR-0010](0010-orchestrator-explicit-data-flow.md): `structural-scan`'s "MR scope" changes — once the gate opens it is proposed like any other node, and the codebase walk that used to be `refactor-scan`'s own inline work moves to `refactor-design`, run only for the chosen candidate.

Two gaps surfaced testing the suite end-to-end against a real target repo (a legacy PHP fixture with zero tooling). First, `refactor-scan` and `refactor-prioritize` never actually implemented the tree-walking ADR-0005 and ADR-0007 specify — the orchestrator's prose claimed it, `scripts/lib/tooling_tree.py` proved the design out against fixtures, but nothing wired either into the agent-facing skill text. A scan against the fixture found five genuine structural candidates and filed them without any awareness that the repo had no `composer.json`, no CI, no PHPStan — the tree was invisible to the skill that was supposed to walk it.

Second, and separately: the orchestrator's own "scaffold `docs/refactoring/config.md` on the first pass" logic and ADR-0005's "`git` is the only hard requirement" rule are both real suite behaviors with no home in the tree they precede. A target repo's very first state — is this a git repository, has the loop been configured here yet — sat outside the tree that is supposed to describe what's missing before deepening work can start.

This ADR does two things. It pulls both prerequisites into a generic, language-neutral tree root (`docs/tooling-tree.md`): `git` (unchanged from ADR-0005, still never a merge request, still a hard stop) followed by `loop-config`, an ordinary node fulfilled when `docs/refactoring/config.md` exists. Language specializations — PHP today, others later per ADR-0002 — attach their first wave beneath `loop-config`, not beneath `git` directly, since adopting Composer or a CI runner presupposes the loop already has somewhere to record state.

It also folds `refactor-scan`'s own structural walk — the hot-spot analysis and friction-signal hunting that finds candidates like a missing seam or a god method — into the tree itself, as a new node: `structural-scan`. This node's required parents are every leaf of the active language tree (for PHP: `composer-audit`, `phpunit`, `test-runner-if-missing`, `php-cs-fixer`, `phpstan-level-3`, `rector-dead-code`, `rector-type-coverage`). Deterministic tooling settles first — a test suite and static analysis exist to catch what an agent-driven structural change could otherwise introduce silently — before agent-driven scanning starts. All bootstrap/gating logic that used to live partly in the orchestrator's pre-flight checks and partly nowhere now lives entirely in `refactor-scan` itself: it checks `git`, checks `loop-config`, checks the backlog isn't already oversized, then walks the tree for the next node — tooling or, once every leaf resolves, `structural-scan`. The orchestrator becomes a thin loop driver that starts a pass with `/refactor-scan` and lets it decide what, if anything, gets filed.

`structural-scan`'s edges are not standard required edges. ADR-0007 says rejecting a required parent closes every node beneath it permanently. Here that would mean one declined tooling branch — Rector rejected as not worth it on a tiny script, say — could forbid structural refactoring on that repo forever, which defeats the purpose of having declined it rather than never considered it. So these seven edges use a new type, `resolved`, defined only for this node: a leaf that is fulfilled *or* explicitly rejected under `docs/refactoring/out-of-scope/` both count as resolved, and `structural-scan` unblocks once every leaf reaches either state. This is scoped to `structural-scan` specifically — it is not offered as a general third edge type in `CONTEXT.md`'s glossary, to keep the required/recommended vocabulary from ADR-0007 unambiguous everywhere else.

## Considered Options

- **Keep `git` in `docs/php-tooling-tree.md`, treat `loop-config` as orchestrator-only prose (status quo).** Rejected: this is exactly the class of gap the tree exists to prevent — a real prerequisite with no tree node, discoverable only by reading the orchestrator's `SKILL.md` text, and the reason the suite's own dry run missed the target repo's tooling state entirely.
- **Merge `git` and `loop-config` into one root node.** Rejected: they carry different severities. Missing `git` means the suite does not run at all (ADR-0005); missing `loop-config` means the suite runs and self-heals via one ordinary candidate. Collapsing them loses that distinction structurally, not just verbally.
- **Leave structural scanning as an unconditional step in `refactor-scan`, run every pass regardless of tooling state (status quo).** Rejected: this is what produced five structural candidates against a repo with no safety net at all — no tests, no static analysis, nothing to catch a regression the loop itself might introduce while "deepening" that code.
- **Gate structural scanning with a standard required edge from each PHP leaf.** Rejected: a single rejected leaf (e.g., the team declines Rector) would then close `structural-scan` forever, per ADR-0007's required-edge semantics — permanently forbidding the loop's actual purpose over one declined tooling branch. The `resolved` edge type exists specifically to avoid this.
- **Formalize a second, parallel `engineering-skills-setup` node** covering the `setup-matt-pocock-skills` precondition (`docs/agents/issue-tracker.md`), a gap of the identical shape discovered during the same investigation — the suite's `README.md` claims "the orchestrator points that out" if it's missing, but nothing checks or tests this. Deferred, not rejected: real gap, same shape as the one this ADR fixes, but independent of `structural-scan`'s tooling gate — folding it in here would conflate two separate fixes into one change.

## Consequences

`docs/tooling-tree.md` is the new generic root: `git` → `loop-config`, both described there. Neither is ever proposed as a merge request in the same sense the tooling nodes are — `git` because it is the one hard stop, `loop-config` because it is an ordinary but suite-internal node whose one candidate is filed by `refactor-scan` itself.

`docs/php-tooling-tree.md`'s edge table changes: `composer` and `ci-runner`'s required parent becomes `loop-config`, and its seven leaf nodes each gain a `resolved` edge into `structural-scan`. Every other PHP node is unaffected.

`scripts/lib/tooling_tree.py` gains a `loop-config` detection function, loads `docs/tooling-tree.md` alongside `docs/php-tooling-tree.md` to build the combined graph, and gates `structural-scan` with dedicated `resolved` logic separate from the existing required-parent gating (a rejected required parent still closes its child; a rejected `resolved` parent does not). The six fixture `expected/roadmap.json` files under `fixtures/php/` are updated to match the re-parented edges.

`refactor-scan` gains concrete precondition checks ahead of its existing process: no `git` stops the pass with nothing filed; a missing `loop-config` files exactly that one candidate and stops; an already-oversized backlog (five or more open `refactor:candidate` issues) stops without filing more. Past those checks, it walks the tree for the next node — a tooling candidate if the PHP tree isn't resolved yet, or its original hot-spot walk if `structural-scan` has opened. `refactor-prioritize` recognizes a proposable tooling-tree node, including `loop-config`, as a strong default recommendation without forcing it. `refactor-design` skips grilling for tooling-tree candidates — their merge-request scope is already fully specified in the tree docs — and grills only structural candidates as before.

Language detection (how a skill decides a target is PHP) stays an informal heuristic, not part of this ADR; formalizing it is premature before a second language specialization exists (ADR-0002).
