# `php-structural-scan`: a language specialization's own aggregation node before `structural-scan`'s gate

> Amends [ADR-0008](0008-generic-tool-tree-and-structural-scan-gate.md): `structural-scan`'s seven PHP-tree `resolved` edges (plus ticket 41's `editorconfig`, an eighth) are replaced by one `resolved` edge from a new PHP-tree node, `php-structural-scan`, which itself aggregates the seven.

ADR-0008 designed `structural-scan` to be shared across future language specializations (`docs/tooling-tree.md`'s intro paragraph, `tree-walk-prompt.md`'s tree-loading step) — PHP today, others later per ADR-0002. But it wired PHP's contribution as seven direct `resolved` edges into the generic root's own node instead of one aggregated edge. `tooling-tree.md`'s `structural-scan` node already had to hedge its leaf-set prose around "the active language specialization's own tree" as a result — workable with one specialization, but the leaf set stops being locally enumerable from `tooling-tree.md` alone the moment a second one exists, and every specialization's own leaf count then shows up directly in the generic root's resolved-parent count.

Raised directly by the user, questioning why `resolved` needs to be its own edge type at all rather than something expressible via `required`/`recommended`, and proposing a generic cross-cutting aggregate node with `recommended` fan-out as an alternative. That generic version was examined and rejected first: it needs the fan-out edges inverted (leaves as parents of the aggregate, not the other way the user first proposed) to get any gating effect at all, and even then a `recommended`-gated node is only made *proposable* once its parents are decided — it still needs a node kind that is "fulfilled" purely by virtue of being proposable, which the engine has no notion of today. The PHP-tree-local variant here avoids that: it keeps reusing the existing `resolved` edge type (still fulfilled-or-rejected, not decided-vs-undecided), just moves where the seven edges terminate.

## Decision

Introduce `php-structural-scan`, a node owned entirely by `php-tooling-tree.md`:

- The seven PHP leaves' `resolved` edges are repointed from `structural-scan` to `php-structural-scan` (same edge type, same seven rows, new target).
- One new `resolved` edge, `php-structural-scan → structural-scan`, is declared in `php-tooling-tree.md` (per the tree's existing ownership rule — one endpoint lives in the language tree).
- `php-structural-scan` is resolved by the identical `resolved`-edge rule as `structural-scan` itself, one hop down: resolved once every one of its seven resolved-parents is fulfilled or recorded as rejected. It has no fulfilment check, no MR scope, and no tool of its own — pure aggregation plumbing, never itself proposed.
- `structural-scan`'s own resolved-parent count in `tooling-tree.md` drops from eight (seven PHP leaves plus `editorconfig`) to two (`php-structural-scan`, `editorconfig`) and stays at two as further specializations are added — each contributes one more direct parent the same way, not N more leaf edges.
- `skills/refactor-scan/references/tooling_tree.py`'s resolved-gate computation, previously hardcoded to the literal string `"structural-scan"` in four places, is generalized to any node with `resolved_parents` entries. `load_tree()` derives an `exposed_resolved_gate_nodes` set from the edge table itself (a resolved-gated node that is itself another resolved-gated node's resolved-parent is never exposed) instead of a second hardcoded name — so a future `js-structural-scan` needs no code change here, only doc/edge-table changes, the same way ticket 41's `editorconfig` leaf needed none.

## Considered Options

- **Status quo — N direct leaf edges per specialization.** Rejected: doesn't scale past one specialization; the generic doc already has to hedge its own leaf-set prose around "whichever tree is active" instead of stating a fixed count.
- **A second hardcoded `"php-structural-scan"` string literal alongside `"structural-scan"` in the parser.** Rejected: doesn't generalize to a third specialization without a third hardcoded string — exactly the shape this ADR sets out to avoid, and the same generalization move ADR-0016 already made for `recommended`-edge gating.
- **A generic cross-cutting aggregate node (`php-tool-tree-resolved`) with `recommended` fan-out**, the alternative first proposed. Rejected: needs the fan-out direction inverted to get any gating effect (leaves become the aggregate's parents), and even then only makes the aggregate *proposable*, not "fulfilled" — the engine has no node kind that is auto-fulfilled once decided, so this would still need new machinery beyond what a `resolved`-edge aggregation node already provides for free.
- **Fold `structural-scan` itself into a per-language node** (e.g., `refactor-design` operates on `php-structural-scan` directly, no shared generic gate). Rejected: loses the entire point of ADR-0008 — one shared name and gate across specializations for the structural-refactoring phase; every downstream consumer (`refactor-design`, `refactor-prioritize`, `SKILL.md` prose) would have to become language-aware where it currently isn't.
- **Accepted: one aggregation node per specialization, generalized resolved-gate logic in the parser.**

## Consequences

`tooling-tree.md`'s `structural-scan` node states a fixed two-parent picture (`editorconfig`, the active specialization's own aggregation node) instead of hedging around an open-ended leaf set. `php-tooling-tree.md` gains one new internal node with no MR scope, documented as never proposed. `tooling_tree.py` gains a `_resolved_gate_status` helper and a derived `exposed_resolved_gate_nodes` set instead of a second hardcoded node name; `next_candidates()`, `roadmap()`, and `withheld_candidates()` all read that derived set to keep `php-structural-scan` out of every proposal/withheld output. `_composer_audit_extra_gate()`'s fallback (proposable once every *other* leaf is resolved) is repointed to read `php-structural-scan`'s resolved-parents — its true siblings under the new shape — rather than `structural-scan`'s own, now-different, two-entry set. All 7 fixtures under `fixtures/php/*/expected/roadmap.json` are regenerated; no roadmap step-count or order shift in any of them, since `php-structural-scan` was never a proposable roadmap step either before or after (confirmed per fixture, not assumed). A future second language specialization (ADR-0002) follows this exact pattern: one `<language>-structural-scan` node, its own leaves feeding it, one edge out to the generic root.
