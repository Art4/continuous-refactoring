# Bookkeeping writes go through their own merge request, never straight to the default branch

> Amends [ADR-0009](0009-merge-request-outlook-and-delivered-label.md): the labels, description shape, and outlook rules decided there are unchanged. What changes is how `refactor-learn`'s writes physically land — through their own merge request, not a direct commit to the default branch.
>
> Amended by [ADR-0012](0012-remembered-merge-requests-follow-the-tracker.md): this rule no longer applies to `docs/refactoring/merge-requests.md` when the target's issue tracker natively supports labels — there is nothing to commit in that case. It still governs `config.md`, ADRs, `CONTEXT.md`, and `merge-requests.md` itself when the target has no such tracker.

Manual end-to-end testing surfaced a real incident: `refactor-learn`'s closing call committed bookkeeping (the merge-requests ledger) directly to the default branch instead of going out through a review. Tracing it back, the gap was structural, not a one-off mistake: `refactor-implement` checks out the candidate branch, pushes it, and opens its merge request, but never switches the working tree back to the default branch afterward. `refactor-learn` runs immediately next and its own prose only asserted *where* its writes should conceptually end up ("this ledger lives on the default branch") without ever saying *how* to get there — no instruction to check out the default branch, no instruction to verify the current branch first, and, most importantly, no instruction that these writes must go out through a review rather than a direct push. An agent following the skill literally has no guardrail against committing bookkeeping onto whatever branch happens to be checked out, or against pushing straight to the default branch outright.

## Considered Options

- **Fold the bookkeeping into the candidate's own already-open merge request (from `refactor-implement`).** Rejected: the entire point of remembering an in-flight merge request in `docs/refactoring/merge-requests.md` is so a *later* pass's `refactor-prioritize` can see it before that candidate merges. If the ledger entry only exists inside the candidate's own unmerged branch, the default branch's ledger stays stale until that candidate merges — reintroducing, at the cross-pass level, exactly the same-pass staleness bug ADR-0010 already fixed by splitting `refactor-learn` into an early and a closing call. It's also awkward for a ledger entry to record its own merge request's URL before that merge request exists.
- **Keep committing bookkeeping directly to the default branch (status quo reading of ADR-0009).** Rejected: this is the bug. It violates the suite's own git convention (own branch, reviewed before landing) and the explicit product requirement that suite state changes always go out through a review, never a direct push to the default branch.
- **`refactor-learn` opens (or reuses) its own small, dedicated bookkeeping merge request against the default branch.** Accepted. It satisfies "always through a review" cleanly, keeps the ledger/ADR/`CONTEXT.md`/`config.md` changes visible for review like any other change, and doesn't block on the candidate merge request's own review cycle.

## Consequences

`refactor-learn` always lands its writes — in either its early or closing call — via a dedicated bookkeeping branch/MR opened (or reused, if one from an interrupted pass is still open) off the default branch, using the same create-mode policy the orchestrator already defines for candidate merge requests. It never writes to whatever branch happens to be checked out, and never pushes directly to the default branch.

The sole exception is the `loop-config`-in-flight case: `docs/refactoring/config.md` doesn't exist anywhere except the `loop-config` candidate's own branch until that candidate's merge request merges, so the handful of fields `refactor-learn` needs to write before then (`Pending issue`, `Create-mode`, `Fulfilled nodes`) ride along in that already-open, already-reviewed merge request instead of getting a separate one. Once `loop-config` merges, every closing call after that opens its own dedicated bookkeeping branch/MR as usual.

The dedicated bookkeeping merge request may sit open briefly before merging, so a subsequent pass's read of the default branch could momentarily lag behind it. This is accepted as the same kind of eventual consistency the loop already tolerates for candidate merge requests — `refactor-scan`'s existing reconciliation step is what notices "merged now" / "closed now" drift later; no new mechanism is needed for the bookkeeping merge request.

This ADR is maintainer-facing paper trail only — no skill cites it by number (per the suite's own "no unresolvable internal ADR citation" convention); the rule itself is stated inline, in plain prose, in `refactor-learn` and `refactor-implement`.
