# Suite merge requests always stack; never branch parallel off the default branch

> Does not amend or supersede [ADR-0011](0011-bookkeeping-goes-through-its-own-merge-request.md): that ADR's decision — `refactor-learn`'s bookkeeping writes go through their own dedicated merge request, based off the default branch, independent of the candidate's own review cycle — is unaffected and stays exactly as decided there. This ADR only changes how *candidate* merge requests (`refactor-implement`'s output) are based when a second one can be opened while one is already in flight (`continuous-refactoring/SKILL.md`'s "Opening a merge request" guidance, "While fewer than two suite merge requests are open, a pass may deliver one more").

A real reviewer-loop observation run surfaced repeated merge-conflict churn on `docs/refactoring/config.md`, traced to the previous stacking rule: "stack (base = the open branch) only when the new candidate is a tooling-tree child of what is in flight or the design depends on it; otherwise branch parallel off the default branch." Two unrelated candidates branching in parallel off the default branch both edit `config.md` bookkeeping fields (originally `Pending candidates`; the same risk now applies to ticket 32's new `Skip streak` field) independently, and the second one to merge conflicts with whatever the first one already changed there.

## Considered Options

- **Fold bookkeeping writes into the candidate's own merge request**, removing the separate bookkeeping merge request entirely. Rejected — this is exactly the option ADR-0011 already considered and rejected, for a reason that still holds: a later pass reads `config.md` from the default branch, and if bookkeeping only exists inside the candidate's own unmerged branch, that later pass sees stale state until the candidate merges.
- **A persistence mechanism for `config.md` fields that tolerates concurrent writes** (e.g. one file per field, or per entry, so two branches touching different fields/entries never collide) — rejected as disproportionate: it would ripple through every existing field (`Fulfilled nodes`, `Pending candidates`) for a problem that has a much smaller fix available at the branching-policy level, and `refactoring-config.md` already deliberately keeps the file's shape simple (flat fields, no per-entry metadata) for the same reason.
- **Always stack candidate merge requests, never branch parallel off the default branch while one is open.** Accepted. At most one candidate branch is ever open against the default branch at a time, so at most one merge request is ever mid-review with a base of `config.md`-as-it-was-before that candidate. Combined with `refactor-learn` reusing an already-open bookkeeping merge request rather than opening a second one (already the documented behavior), this means only one write to `config.md` is ever in flight at once, from either source.

## Consequences

`continuous-refactoring/SKILL.md`'s "Opening a merge request" section now always bases a second suite merge request on whatever suite branch is currently open, never on the default branch directly, for as long as one is open. The tradeoff is throughput: a pass can no longer deliver two genuinely unrelated candidates in parallel — the second always waits behind the first, even when nothing about their content actually conflicts. This is accepted because `config.md` correctness (no silent bookkeeping-write conflicts) matters more than that modest parallelism, and the loop was already only delivering one candidate per pass in the common case.

This does not change `refactor-learn`'s own bookkeeping-merge-request policy (ADR-0011): it still bases off the default branch, still reuses an interrupted pass's still-open bookkeeping merge request rather than opening a new one, and still doesn't block on the candidate merge request's own review cycle. The candidate branch itself never touches `config.md` — only the bookkeeping merge request does — so the two don't need to stack on *each other*; what changes is only that two *candidate* branches can no longer both be open against the default branch at once.

This ADR is maintainer-facing paper trail only — no skill cites it by number, per the suite's own convention; the rule itself is stated inline, in plain prose, in `continuous-refactoring/SKILL.md`.
