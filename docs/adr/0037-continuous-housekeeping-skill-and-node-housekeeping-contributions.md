# A separate `continuous-housekeeping` skill, fed by an optional `Housekeeping` field on tooling-tree nodes

The tree has always assumed a node's own Fulfilment check is a one-time artefact question: is the tool adopted, correctly, right now. Nothing kept "adopted but not actually being kept current" concerns on anyone's radar — dependency versions drift, tooling-deprecation warnings surface only after a manual re-run, and CI-gated concerns like `composer audit` only catch what's wrong *at the moment CI runs against an unchanged lockfile*, never what becomes wrong later against that same, still-passing lockfile. Grilled from scratch, starting from "should this be a tree node at all," per the ticket's own note that it was the least-designed of several ideas parked during an earlier grilling session.

## Considered Options

- **A recurring tooling-tree node**, re-proposed once its last pass is older than some interval — the shape originally sketched. Rejected: `tooling_tree.py`'s deterministic parser has zero forge access, so it can't derive "when was the last one" from tracker history the way a genuinely useful cadence check needs to; forcing this into the tree would need a new, purely time-driven fulfilment flag with no real precedent (`php-minimal-version`'s own re-triggering, ADR-adjacent, is *fact*-driven — a moving target being compared against, not a timer). It would also strain the tree's `resolved`-gate assumption that a leaf, once resolved, stays resolved (`structural-scan`'s own gate reads leaves that way).
- **One fixed, hardcoded checklist inside a new skill**, mirroring a real-world reference example's own bundle (composer update, PHPStan deprecations, PHP patch/minor, dependency-doc sync, outdated/audit review) directly. Rejected: nearly every one of those concerns is PHP/Composer-specific, and hardcoding them into a skill meant to sit at the generic root (usable regardless of which language tree, if any, a target has) would misplace PHP-specific knowledge outside the PHP tree, the opposite of how every other PHP-specific concern in this suite is organized.
- **Bundling this into `continuous-refactoring`'s own pipeline** (a sixth lifecycle step). Rejected: housekeeping's own trigger (a calendar interval) and unit of work (a checklist sweep, not a single structural/tooling candidate) don't fit the scan → prioritise → design → implement → learn shape at all — it isn't ranking or delivering one candidate, it's working through a standing list.

## Decision

**A new, standalone skill, `continuous-housekeeping`**, structurally a peer of `continuous-refactoring` itself (its own entry point, its own trigger) rather than a step inside it or a tooling-tree node:

- **Cadence**: configurable per target, default weekly, decided once via the skill's own tiny setup interview (one question) the first time it runs with nothing recorded yet — mirrors `loop-config`'s own interview pattern at a much smaller scale. Recorded as a new `Housekeeping cadence` field in `bookkeeping.md`, alongside every other loop-adjacent setting — but read only by this skill; the continuous-refactoring loop itself still has, and needs, no cadence of its own.
- **Due-check with no stored "last run" state**: search the tracker for the most recent `Housekeeping — <date>`-titled issue and compare its age against the cadence. No date field to keep in sync, no risk of it drifting from reality — the tracker's own history is authoritative, the same way `merge-requests.md`/native tracker linkage already is the record for in-flight suite MRs elsewhere in this suite.
- **Generic mechanism, PHP-specific content, cleanly separated by layer**: the skill itself (cadence, setup interview, tracker-agnostic due-check, one standing item — an AGENTS.md/skills/rules sync check that belongs to no single tool) is entirely generic, usable regardless of language. What actually gets checked each cycle is **contributed by individual tooling-tree nodes**: a node's own doc may name an optional `Housekeeping` field (documented once, generically, in `CONTEXT.md`'s **Tooling tree** entry — not re-explained per tree). Ordinarily, when that node's own delivering merge request lands, the MR also appends the node's `Housekeeping` line to the Refactoring Notes' `housekeeping-template.md`, creating the file fresh if it doesn't exist yet.
- **Reconciliation against `Fulfilled nodes`, every cycle**: the delivering-MR path alone leaves every node fulfilled *before* a target adopts `continuous-housekeeping` — the common case, not an edge case, for any target with existing tree progress — with no future delivering MR left to carry its line. Caught live during review, on the very target this whole mechanism was designed against: `Art4/legacy-todo` had `composer`/`composer-audit`/`phpstan-deprecation-rules` all fulfilled well before this skill existed, so none of them would ever have reached the template file under the delivering-MR path alone. Fixed by having `continuous-housekeeping` itself read `bookkeeping.md`'s already-open `Fulfilled nodes` cache every cycle and append any missing `Housekeeping` line it names — cheap (the field is already being read for the cadence check), and repeated every cycle rather than once so a `Fulfilled nodes` cache briefly lagging behind reality doesn't cost a contribution permanently. `continuous-housekeeping` still never walks the tree itself (`tooling_tree.py`/`detect_nodes()`) — it only ever reads the cache another skill already maintains.
- **One issue per due cycle**, its checklist assembled from the template file's current contents plus the standing item — not several independently-recurring per-concern checks.
- **`php-minimal-version` exception**: this node's own `Housekeeping` line (check for a newer PHP patch/minor of the declared floor — a *currency* concern, distinct from that node's own Fulfilment check, which only asks whether the floor is *correct*) normally rides its own delivering MR like any other node. If the floor already satisfies everything on the very first scan, that node never gets a delivering MR at all — so `loop-config`'s own first MR contributes the line instead, the one place this exception needs stating.
- **Explicitly out of scope for this decision**: Psalm's own `psalm-baseline.xml` findings — structurally similar to PHPStan baseline entries, but a security-relevant backlog (taint findings) deserves the same continuous, pass-by-pass treatment PHPStan's own baseline-shrink mechanism already gets, not a once-a-cycle sweep. Left for its own, separate ticket to transplant that mechanism onto Psalm's format.

## Consequences

A target repo can now keep "adopted but not verified current" concerns from silently rotting — dependency drift, newly-surfaced deprecations, unreviewed audit findings past the moment CI last checked them — on the same kind of standing cadence real-world maintenance practice already uses, without forcing a fundamentally time-driven concept into a tree model built around one-time, fact-driven fulfilment. Every future tooling-tree node gets to state its own recurring concern, if it has one, in the same place it already states its Fulfilment check and MR scope — no second registry to keep in sync. A target that never adopts `continuous-housekeeping` pays no cost: node MRs still land normally, they just also leave a line in a file nothing reads yet.
