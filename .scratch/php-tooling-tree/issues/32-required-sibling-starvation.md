# 32 — `refactor-prioritize` has no anti-starvation factor for `required` tooling siblings (`php-cs-fixer` never chosen across 9+ passes)

**What to build:** Add a fifth ranking factor — **Skip streak** — to `refactor-prioritize`'s step 2 (alongside Heat, Leverage, Tooling pressure, Risk): how many consecutive prior passes proposed this candidate without choosing it. A longer streak should weigh increasingly toward choosing it this pass — a soft signal folded into the ranking reasoning, not a hard override/force rule. Persist the streak as a new `Skip streak` field in `docs/refactoring/config.md` (a node-slug-keyed bullet list, the same shape as `Fulfilled nodes`), written only by `refactor-learn` (the suite's sole bookkeeping writer, ADR-0010) as an extension of its existing closing-call write step: increment every `required` tooling node that was proposable this pass but not chosen; reset to 0 for the node that was chosen or newly fulfilled.

Because `skills/continuous-refactoring/references/refactoring-config.md` explicitly documents "No per-entry metadata [...] invites merge conflicts between bookkeeping writes" as an anti-pattern — and that exact pattern already caused repeated bookkeeping-MR conflicts via the singular `Pending issue` field (observation finding, see Comments) — also change `skills/continuous-refactoring/SKILL.md`'s branching rule: from "stack only when the new candidate is a tooling-tree child of what's in flight, otherwise branch parallel off the default branch" to **always stack, never branch parallel off the default branch, while any suite MR is open**. This structurally eliminates two concurrently open branches ever touching `config.md` at once. ADR-0011 (bookkeeping gets its own MR rather than riding in the candidate's MR) stays unchanged — it already considered and rejected folding bookkeeping into the candidate MR, for a reason that still holds (staleness: a later pass wouldn't see bookkeeping changes until the candidate MR merges). Document the new stacking rule in its own ADR.

**Why:** Observed on a real run (`Art4/legacy-todo`, reviewer-loop playbook, watched agent: opencode). A `/grill-me` sub-agent analyzed opencode's own session transcript (`file:///home/artur/Downloads/new-session---2026-08-29t15-58-55-178z.json`, 184 messages) and established the following:

- The deterministic parser (`tooling_tree.py`) ran **9 times** directly (e.g. messages 19, 20, 38, 53, 60, 69, 108, 119, 127), returning valid JSON every time — `python3` was available throughout the whole session. The LLM fallback (`tree-walk-prompt.md`) was **never** read or needed.
- opencode reads the suite's own `SKILL.md` files directly (messages 1, 3) and instructs every dispatched sub-agent round to do the same (12 occurrences) — not a third-party reimplementation in the sense the ticket originally suspected.
- **`php-cs-fixer` appeared in every parser `next` result from round 4 onward**, correctly reported as unblocked (messages 69, 108, 119, 127) — the scan/proposal step never failed.
- **`refactor-prioritize` (or opencode's faithful execution of it) explicitly deprioritized `php-cs-fixer` in every one of rounds 4 through 12**, with plausible per-round reasoning in favor of a different candidate each time (e.g. "PHP CS Fixer is lower-leverage" [message 71], "only feeds recommended edges" [111], "only styles and doesn't reduce the baseline" [136], "would raise merge-conflict churn with the in-flight Rector MR" [173]). It was never filed as an issue — confirmed live via `gh issue list --repo Art4/legacy-todo --search "cs-fixer"` (empty).
- `composer-audit` never appeared in any `next` result, but **correctly so**: its documented stop-condition (a real `require` dependency OR every other `structural-scan` leaf resolved) was never met at any point (`composer.json`'s `require`, per the transcript's message 2397, is only `{"php": ">=5.6"}` — no real dependency). **Not a bug — working as designed.**
- `skills/refactor-prioritize/SKILL.md`'s four ranking factors (Heat, Leverage, Tooling pressure, Risk) have no memory of prior deprioritizations — a `required` sibling that structurally never shines on those four axes can starve indefinitely, exactly the observed behavior.

This disproves the ticket's original hypothesis (bug in the parser, the fallback prompt, or a third-party reimplementation) — the real cause sits in `refactor-prioritize`, a component the original checklist didn't even list as a possible culprit.
